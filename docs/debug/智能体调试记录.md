### 人员检测 skill 边界

启动脚本 3 后，可以通过摄像头检测人物。`check_person_detected` 不应该变成“检测算法”或“常驻监听服务”，而应作为检查工具使用：

- `sensing_node` 是否在运行。
- `/track_pose` topic 是否存在。

## 2026-04-26

![agent 调试截图](../images/agent-image-1.png)

启动智能体之后，尝试进行底盘操作命令。首先测试简单前进，可以直接执行；当进入复杂任务或风险任务时，agent 会返回可选择方案，或要求补充参数，并在二次确认后执行。

### 问题 1：导航过程中的定位和碰撞风险

在使用智能体控制时，偶尔会出现无法导航到目标点，或在导航过程中发生碰撞。按预期，agent 只是向 `move_base` 发送目标坐标，车端已有自动导航和自动避障，不应由 agent 直接造成碰撞。

测试中发现，agent 下发指令给中车后，行驶过程中雷达点云逐渐偏离，没有完全贴合地图。后续测试大多数情况下仍能到达目标点，但边界还不清楚，需要继续优化和验证。

### 问题 2：目标点姿态换算可能带来误差

为了排除变量，重写导航 skills 和适配服务。目前配置文件中设置的目标点位为 `x/y/yaw`，适配服务根据 `yaw` 转换为 `z/w`。这一步转换可能导致精度下降或较大偏差。

测试中曾出现：当 agent 命令无人车去一个与当前位置相反方向的目标点时，无人车显示路径规划失败、不可达；手动遥控更改朝向后，又能到达目标点。该情况只出现过一次，具体原因未确认。

后续可以考虑直接保存实际读取到的 `orientation`，不再通过 `yaw` 二次转换，按 `move_base` 所需标准数据格式输入，减少二次计算误差。

```yaml
header:
  seq: 0
  stamp:
    secs: 0
    nsecs: 0
  frame_id: "map"
pose:
  position:
    x: 目标点x
    y: 目标点y
    z: 0.0
  orientation:
    x: 0.0
    y: 0.0
    z: sin(yaw / 2)
    w: cos(yaw / 2)
```

### 问题 3：目标发布接口差异

当时的 skills 发送到 `/move_base/goal`，RViz 的 `2D Nav Goal` 发送到 `/move_base_simple/goal`。两者目标含义接近，但为了减少无关变量，曾考虑将程序发布话题也改为 `/move_base_simple/goal`。

后续修复记录中已确认：`/move_base_simple/goal` 缺少 action result 回调，不适合作为需要准确成功/失败语义的主链路。导航结果语义应优先依赖 `move_base` action。

### 问题 4：巡逻和多技能队列

导航功能的进阶方向是实现巡逻功能，同时实现多目标顺序执行队列，让 agent 能够调用多个技能，并在接收到 skill 回复后再执行下一步，增强状态管理。
